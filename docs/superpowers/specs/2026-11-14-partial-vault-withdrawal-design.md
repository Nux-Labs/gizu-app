# Requested vault withdrawal portions

The owner authorizes implementing an amount choice end to end, retaining the remaining investment, returning proceeds to private USDC Account 2, preserving approvals, regression testing and installing the production app. Their model is that the requested portion is the whole withdrawal operation. No additional design approval loop is needed.

## Approach

Keep the existing redemption and private-return stages and existing operation IDs. Extend their proposals with explicit optional portion fields; old full-withdrawal proposals retain their current rules. The selected share amount is the complete redemption for this operation, not the entire investment wallet's share balance. Adding only an input would fail native validation; withdrawing everything and redepositing the remainder would unnecessarily move the retained investment.

One vault-level amount is entered in USDG before fees, with Max available. Read fresh per-wallet public shares/previewRedeem capacities, allocate in the existing cycle/slot order, and redeem only the requested amount (full earlier wallets and a bounded partial final wallet). Untouched wallets remain untouched. Capacity observations are display/planning data, never spending authority. Native code independently reads previewRedeem for the selected shares, bounds its current USDG value to the requested amount, and verifies the held shares before approval and signing. All calculations use base-unit integers and ERC-4626 rounding, never floating-point.

## Contracts

- Withdrawal request: optional `requestedWithdrawalAtoms` (USDG assets), `withdrawalRequestId`, and `withdrawAllShares: true` for a Max/full-wallet portion. Absent fields retain the legacy full-withdrawal rules. The backend resolves an ordinary amount with previewWithdraw; Max selects every held share without a rounding round-trip. Signed `amountAtoms` is always the exact selected shares. Native code independently reads previewRedeem(selected shares), requires positive held/selected shares, and bounds assets to requested minus one base unit through requested plus max(one base unit, 10 bps). It applies the bound at prepare and signing; the native prompt shows the preview, exact shares, fees and tolerance. Every other state/continuity check remains strict. The existing kind-dependent preview state field is reused; no UniFFI layout change is needed.
- Private return: optional `withdrawalOperationId` and `returnBudgetAtoms`, bound to a finalized native redemption in the same wallet/cycle/slot. Its actual Withdraw event establishes the gross proceeds. The backend budgets only these proceeds, leaves unrelated public reserves intact, and permits remaining vault shares. While shares remain, it replenishes the existing next-withdrawal reserve (2.6 times the source redemption’s approved fee cap) from proceeds; native authorization independently checks this floor and balance coverage. An explicitly supplied native reserve remains honored if holdings change later. Native admission independently validates the source ID, exact scope, finalized receipt, positive proceeds, spend-plus-fee cap, and non-reuse by another signed return. Existing quote/baseline/minimum credit verification and Account 2 derivation remain authoritative.
- Receipt reconciliation checks the exact approved share burn and Withdraw assets. A requested partial redemption projects withdrawn when that portion succeeded even with nonzero residual shares. Native inventory keeps activity invested after its private return completes. A later requested portion is new work; prior completion stays terminal.
- A wallet/profile-scoped saved UI request contains request ID, total atoms and allocated portions with their cycle/slot and asset amount. It carries no signing authority. Native proposals/public journals expose request/source IDs, selected amounts and Max mode, allowing retries/reopening to recognize existing signed operations instead of creating duplicates. Pending native work is always recovered before another amount can be entered. Missing or malformed UI cache falls back to native recovery without widening a requested amount. Existing legacy pending withdrawals/payouts retain their original recovery screen. Replacing a completed UI request requires a new user-entered amount and new approval. Completion IDs are projected from native receipts, so an older request stays complete across a later partial withdrawal. Canceled async reads queue the latest replacement and ignore stale wallet results. Native-retired signed retries must use the same EntryPoint nonce; one canonical winner cancels its competing bytes. Expired attempts recover only canonical receipts and cannot become sendable again. Other incoming private credits remain serialized, and automatic continuation stops if its exact redemption loses the nonce; a winner needs a fresh source-bound return review.
- Completion is scoped to the saved request's portions. It never marks a remaining investment as fully exited or populates the full-exit cache. On completion show the requested withdrawal complete and retain the remaining vault value and a deliberate next-withdrawal action.

## Bounds and compatibility

Whole-request preflight checks every allocated portion’s fork redemption and private-route feasibility before any approval. It rejects a tiny/unroutable portion without first executing earlier portions. The fee envelope is conservative (4 times the redemption cap with shares remaining; 2.6 times when fully exiting); fresh authoritative return quotes still follow the actual receipt and may change.

Zero, invalid precision, over-balance, stale references and amounts too small to redeem/route fail before spending where they can be determined. The review states gross withdrawal and fees; the private USDC minimum remains quoted after the canonical redemption receipt. No new history API, account, general spending session or automatic financial action is introduced. Existing full withdrawals, historical completion corrections, pending legacy payouts, source funding and deposits retain their rules. New capability negotiation prevents new proposals reaching old native code; old backend strict schemas fail visibly rather than silently falling back to full redemption.
